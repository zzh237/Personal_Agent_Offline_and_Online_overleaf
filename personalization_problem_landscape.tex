\section{Setting}
\label{sec:setting}

\paragraph{Evidence base.}
Two project PRISMA runs yielded 6{,}663 raw records and 119 full-text reviews.
We cite primary papers for their methods and evaluation settings, not as
evidence that our policy works.

\paragraph{One user is the unit of personalization.}
For user $u$, the offline history
\[
  \history
  =
  \{\text{thoughts, conversations, corrections, preferences,
  task states, actions, tools, and outcomes}\}
\]
produces an initial checkpoint $c_u^{(0)}$.  After deployment, interaction
batch $\stream$ is generated by the active checkpoint $\checkpoint$.
The update is
\begin{equation}
  c_u^{(t+1)}
  =
  \mathcal A\!\left(c_u^{(t)},\history,D_u^{(1:t)}\right).
  \label{eq:update}
\end{equation}
Each record stores its user, time, task, checkpoint, trace, feedback source,
and training eligibility.  A shared prior is allowed; raw histories remain
separate.

\paragraph{A policy update is required.}
Retrieval, profiles, memory, and decoding control are baselines, not the
learned object.  OPPU trains a private user adapter
\citep{tan2024oppu}; P-RLHF trains a user-conditioned policy
\citep{li2024personalized}; and SPRInG updates a user adapter over time
\citep{kim2026spring}.  CoSteer is tuning-free
\citep{lv2025costeer}, while FABLE learns an external execution policy around
a frozen agent \citep{jin2026fable}.  Neither CoSteer nor FABLE updates a
deployed user's language-model policy weights.

\paragraph{Objective.}
Improve personalization without degrading task success or safety:
\begin{align}
  \max_{\mathcal A}\quad&
  \mathbb E[\upers(c_u^{(t+1)})] \nonumber\\
  \text{s.t.}\quad&
  \mathbb E[\utask(c_u^{(t+1)})-\utask(c_u^{(t)})]
    \ge -\delta_{\mathrm{task}}, \nonumber\\
  &
  \mathbb E[\usafe(c_u^{(t+1)})-\usafe(c_u^{(t)})]
    \ge -\delta_{\mathrm{safe}}, \nonumber\\
  &
  \cost_{\mathrm{train}},\cost_{\mathrm{serve}},
  \cost_{\mathrm{feedback}}
  \ \text{remain within declared budgets}.
  \label{eq:constrained-objective}
\end{align}
\paragraph{Exact scope.}
The target is one user-specific model that remains in use over time.  It is
first trained on that user's history, then updated from later interactions
with the same user.  It executes agent tasks, and learning changes its
language-model parameters.  A \emph{live update}
happens after the system is already in use: new interactions change the model,
and the new model replaces the old one.  Replaying a fixed dataset or
collecting data during one training run is not a live update.  Here, a
personalized agent executes tasks for a user by choosing tools, using memory,
taking actions, or asking questions.  Personalized text generation alone is
not agent execution.  No cited method covers all of these properties.

\section{How Prior Work Differs}
\label{sec:problems}

\subsection{Learning the user}

\paragraph{P1: identify preferences from sparse, mixed evidence.}
A user supplies requests, choices, edits, and task outcomes, not one uniform
label.  Population training can blur minority preferences
\citep{li2024personalized,jang2023personalizedsoups}.  CoPL and PROPER share
structure across users \citep{choi2025copl,zhang2025proper}; FSPO adapts from
few examples \citep{singh2025fspo}.  We instead use one user's full history.

\begin{settingpointer}
These methods learn from stored preference data.  Several combine data across
users, and CoPL trains a reward model rather than the LLM that produces
responses.  They do not study an agent that learns from one user's later task
interactions.
\end{settingpointer}

\paragraph{P2: separate lasting preferences from temporary requests.}
A request may express a lasting preference, a task constraint, or noise.
SPRInG detects likely preference changes before updating a user adapter
\citep{kim2026spring}.  In an agent, a bad result may come from a tool or
reasoning error rather than a wrong preference.

\begin{settingpointer}
SPRInG trains a separate LoRA for each user and updates its weights over a
fixed sequence of later text records.  It personalizes text generation, not a
system that executes tasks through tools, memory, actions, or questions.  It
therefore does not test live learning from agent actions and task results.
\end{settingpointer}

\paragraph{P3: learn from little user history without mixing users.}
Collaborative and federated models improve sparse-user adaptation
\citep{choi2025copl,zhang2025proper,zhu2026fedpdpo}.  Our setting may use a
shared base model, but histories, updates, and evaluation remain
user-specific.

\begin{settingpointer}
These methods learn user-specific components from stored data for many users.
PROPER and FedPDPO update LLM components, while CoPL updates a reward model.
They do not learn from a deployed agent.  Our setting starts with a known
user, so learning with no history is not required.
\end{settingpointer}

\subsection{Moving from offline history to live learning}

\paragraph{P4: build an offline model that can still improve later.}
The offline model must complete tasks and still be able to learn.  OPPU
provides a starting model for each user \citep{tan2024oppu}.  WebRL shows that
an agent learns better when it starts from a working model
\citep{qi2025webrl}.

\begin{settingpointer}
OPPU trains an LLM adapter for one user but stops after offline training.
WebRL trains an agent and then improves it with new data collected during
training, but it has no individual user.  Neither tests a deployed
user-specific agent that keeps learning.
\end{settingpointer}

\paragraph{P5: move from offline to live training without losing performance.}
Offline records come from older models.  Bridging studies when to copy new
weights to the model that collects data \citep{lanchantin2025bridging}.
Hybrid preference learning combines stored and newly requested comparisons
\citep{bose2024hybrid}.  Policy expansion keeps the old policy available while
the new one explores \citep{zhang2023pex}.  We must also record the user,
feedback source, and model version for every interaction.

\begin{settingpointer}
These methods start with offline data and later collect new data during
training.  Bridging updates LLM weights; the other papers study more general
optimization methods.  None studies one user's deployed agent.
\end{settingpointer}

\paragraph{P6: learn changing preferences without forgetting stable ones.}
SPRInG selects likely preference changes and keeps difficult past examples
\citep{kim2026spring}.  Stable Asynchrony learns from records produced by older
model versions \citep{huang2026stable}.  We need both while retaining stable
preferences.

\begin{settingpointer}
SPRInG models one user but uses stored text.  Stable Asynchrony updates an LLM
from records produced by older model versions, but has no user personalization
or deployed agent.  Neither studies preference changes in a deployed personal
agent.
\end{settingpointer}

\paragraph{P7: learn from fewer user corrections.}
User feedback is expensive.  Hybrid preference optimization trades offline
data against new queries \citep{bose2024hybrid}.  FABLE learns a per-user
execution policy only during live use \citep{jin2026fable}.  We measure
interactions needed to reach the same score on future tasks.

\begin{settingpointer}
FABLE learns online for one user while the host agent stays unchanged and
executes the task.  It has no learned offline starting point and does not
update the host LLM.
Hybrid preference optimization combines stored data with new queries, but is
not a personalized agent.  Neither trains one personalized LLM across both
phases.
\end{settingpointer}

\subsection{Learning an agent policy}

\paragraph{P8: personalize agent behavior without reducing task success.}
Personalized agents choose tools, memory, clarifications, and response style
while completing the task.  PersonalWAB studies web actions
\citep{cai2025personalwab}, FingerTip 20K studies mobile execution
\citep{yang2026fingertip}, and FABLE adapts execution around an agent that
stays unchanged
\citep{jin2026fable}.

\begin{settingpointer}
PersonalWAB and FingerTip evaluate personalized actions on fixed benchmarks.
FABLE learns an external controller online for each user.  None first trains a
personal LLM from past user data and then continues updating that LLM after
deployment.
\end{settingpointer}

\paragraph{P9: identify which action caused success or failure.}
A correction may follow many reasoning and tool steps.  WebRL learns from a
success or failure signal given only at the end \citep{qi2025webrl}; we must
also identify which steps reveal the user's preference.

\begin{settingpointer}
WebRL updates an LLM web agent from task success and failure, but it has no
individual user and collects data during training.  Our method must also learn
which action reflects the user's preference.
\end{settingpointer}

\subsection{Obtaining credible and affordable evidence}

\paragraph{P10: avoid learning quirks of simulated users.}
UserRL, UserVille, ProPerSim, and CollabLLM train or evaluate agents with
simulated users
\citep{qian2025userrl,sun2025userville,kim2025propersim,wu2025collabllm}.
PersonalLLM creates synthetic preference models \citep{zollo2024personalllm}.
Simulators reduce cost but can impose their own style and reward biases
\citep{rezk2025rmcrisis}; real-user evidence remains necessary.

\begin{settingpointer}
Several papers train or evaluate agents with simulated personas, but they do
not maintain a policy for one real user and update it during live use.
Simulation can support training; it cannot prove improvement for a deployed
user.
\end{settingpointer}

\paragraph{P11: reduce the cost of one model per user.}
Per-user adapters and live training add storage and compute.  OPPU uses
lightweight adapters \citep{tan2024oppu}, CoSteer uses a local model to guide a
cloud model \citep{lv2025costeer}, and FABLE learns a small external policy
\citep{jin2026fable}.  We test whether a compact user policy can match a
larger generic model at lower serving cost.

\begin{settingpointer}
OPPU trains a user's LLM adapter offline.  CoSteer changes generation without
training model weights.  FABLE learns an external controller during live use.
None trains a compact user LLM offline and then continues updating it during
live use.
\end{settingpointer}

\paragraph{P12: test future behavior, not memory of past text.}
LongLaMP provides chronological long-form tasks \citep{kumar2024longlamp};
PrefEval tests preference following \citep{zhao2025prefeval}; PERMA adds
evolving preferences and tasks \citep{liu2026perma}; and PRISM supplies
individual feedback \citep{kirk2024prism}.  Our endpoint is behavior on
untouched future tasks.

\begin{settingpointer}
These are datasets and benchmarks, not training methods.  They contain
per-user histories; PERMA also evaluates task execution.  None updates a
deployed model.
\end{settingpointer}

\section{Claim}
\label{sec:claim}

\begin{quote}
\textbf{A compact, user-owned language model first learns from one person's
past conversations, corrections, and tasks.  It then continues learning from
that person's later agent interactions by updating its weights, without
reducing task success or safety.}
\end{quote}

This requires an offline personal model, later parameter updates, and a
comparison on the same future tasks.  The method specifies how past user data,
new task records, feedback, replay, and model replacement work together.

\subsection{Additional claims}

Report these claims only when their tests pass:
\begin{description}
\item[Fast adaptation.] Fewer real interactions reach the same valid score.
\item[Value of task traces.] Tool actions and verified outcomes improve future
  execution beyond text-only history.
\item[Small versus large.] A compact personalized policy beats a larger
  generic model while preserving task success and lowering cost.
\item[Simulation benefit.] Simulator training reduces real-user interactions
  and survives held-out human evaluation.
\item[Privacy.] The implementation follows its declared data boundary without
  exposing another user's raw records.
\end{description}

\section{Success Criteria}
\label{sec:success}

\subsection{Required checks}

Before comparing scores, every reported update must pass:
\begin{enumerate}
  \item the parent and candidate checkpoint hashes differ;
  \item the candidate loads in a separate worker and produces the evaluated
  task records;
  \item offline training, live updates, validation, and future testing use
  separate time periods;
  \item every training record stores the user, task, generating model,
  timestamp, and feedback source;
  \item failed runs, users, and rollbacks remain in the report;
  \item the simulator, reward model, or LLM judge has not seen the future test
  or its answer.
\end{enumerate}
If any check fails, the run is invalid.

\subsection{Main statistical test}

Let $b$ be the strongest baseline selected on validation data.  Compare it
with the candidate on the same future tasks:
\begin{align}
  \Delta_{\mathrm{pers}}
    &= \upers(c_{\mathrm{candidate}})-\upers(c_b),\\
  \Delta_{\mathrm{task}}
    &= \utask(c_{\mathrm{candidate}})-\utask(c_b).
\end{align}
The main claim passes only when
\begin{equation}
  \operatorname{LCB}_{95\%}(\Delta_{\mathrm{pers}})>0
  \quad\text{and}\quad
  \operatorname{LCB}_{95\%}(\Delta_{\mathrm{task}})
  \ge -\delta_{\mathrm{task}}.
  \label{eq:primary-gate}
\end{equation}
Choose the minimum useful personalization gain and
$\delta_{\mathrm{task}}$ before final evaluation.  Group confidence intervals
by user or related task; repeated turns are not independent samples.

\subsection{Large-model comparison}

The large-model comparison must include:
\begin{enumerate}
  \item a large generic model without personal history;
  \item the same model with the full allowed history;
  \item strong RAG or profile prompting;
  \item a method that changes generation without training, such as CoSteer,
  when executable
  \citep{lv2025costeer};
  \item the compact offline-only model and the same model after live updates.
\end{enumerate}
Match prompts, tools, history, and task budgets.  A compact model wins only if
it improves personalization, preserves task success, and costs less.

\subsection{Adaptation speed}

For threshold $\tau$, measure real interactions rather than training passes:
\begin{equation}
  T_{\tau}
  =
  \min\{n:\upers(c_u^{(n)})\ge\tau
  \ \text{and task/safety gates pass}\}.
\end{equation}
Also report scores throughout learning, the final score, clarifications,
correction time, and rollbacks.

\subsection{Simulator evidence}

Test:
\begin{enumerate}
  \item \textbf{Preference match:} agreement on held-out real-user choices.
  \item \textbf{Method ranking:} whether simulated and real users rank methods
  in the same order.
  \item \textbf{Training value:} whether simulation reduces later real-user
  interactions.
\end{enumerate}
Simulator reward alone does not support a real-user claim.

\paragraph{Evaluation benchmarks.}
Use a chronological stream such as LongLaMP \citep{kumar2024longlamp} and an
executable agent benchmark such as PersonalWAB or FingerTip 20K
\citep{cai2025personalwab,yang2026fingertip}.  PrefEval and PERMA add
long-horizon tests \citep{zhao2025prefeval,liu2026perma}.  Final results need
held-out human feedback or stored real-user records and two different
benchmarks.

\paragraph{Replication.}
Repeat the protocol across independent users.  Report per-user results, the
median, worst decile, and confidence intervals grouped by user, with at least
three runs for early tests and five for final results.

\section{Claims We Must Not Make}
\label{sec:nonclaims}

\begin{itemize}
  \item Replaying old records in time order is not live learning after
  deployment.
  \item Better retrieval or profile recall is not evidence of a better policy.
  \item A simulator-only win is not evidence of real-user improvement.
  \item A changed loss value does not show that the new model was loaded.
  \item A personalized reward-model gain is not automatically a policy or task
  gain \citep{rezk2025rmcrisis}.
  \item Keeping adapters local does not by itself prove privacy.
  \item Beating a large model on style does not mean beating it on task
  capability.
  \item Mean improvement cannot hide severe failures for a subset of users.
\end{itemize}

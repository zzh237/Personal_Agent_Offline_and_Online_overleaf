  \vspace{5pt}
  {\large A Design Note on Personalized Models\par}
  \vspace{4pt}
  {\small August 29, 2026}

\section{Decision}

New user preferences should first stay in a prompt or external memory. This
makes them easy to inspect, change, and delete.

Train a user adapter only when a preference:
\begin{itemize}
  \item appears in several sessions;
  \item remains stable over time;
  \item affects several kinds of tasks; and
  \item should apply even when the prompt does not include a user profile.
\end{itemize}

A parameter update is not the default choice. It must personalize better than
context without reducing task success.

This note proposes a simple test. Use the same user evidence to build two
versions:
\begin{enumerate}
  \item \textbf{Context version:} Store the evidence in the prompt or external
  memory. Do not change the model.
  \item \textbf{Parameter version:} Train a user adapter on the same evidence.
  Do not include that evidence in the test prompt.
\end{enumerate}
Both versions start from the same model and run on the same later tasks.
Choose the parameter version only when it improves personalization and
preserves task success. Otherwise, keep the context version.

This is a proposed experiment. It is not yet a validated algorithm.

\section{Three Forms of User Information}

\begin{table}[ht]
  \centering
  \caption{Each form of user information serves a different purpose.}
  \begin{tabularx}{\textwidth}{@{}L{0.20\textwidth}L{0.34\textwidth}Y@{}}
    \toprule
    Form & Use & Main property \\
    \midrule
    Prompt or external memory &
    Provides user facts, preferences, or history at runtime. &
    Easy to change, but uses context and may retrieve the wrong record. \\
    Training prompt &
    Gives a teacher model instructions for creating a training target. &
    Provides training signal. It is not necessarily part of the deployed
    user state. \\
    User adapter \(\adapter\) &
    Stores parameters learned for user \(u\). &
    Works without repeated profile text, but is harder to inspect and change. \\
    \bottomrule
  \end{tabularx}
\end{table}

In this note, an online update happens after deployment. The system first
serves the user. It then learns from new interactions and creates a new
adapter. Training on a fixed dataset is not post-deployment learning, even
when the training process draws new samples.

A personalized agent must also complete tasks. Changing writing style alone
does not make a system a personalized agent.

\section{What Prior Work Covers}

\paragraph{OPPU.}
OPPU trains one parameter-efficient fine-tuning (PEFT) module from each user's
history \cite{tan2024oppu}. It can also use retrieval or a user profile. OPPU
is an offline method. It does not update from later deployed interactions.

\paragraph{Personalized DPO.}
Personalized RLHF learns user representations and LoRA parameters from offline
preference data \cite{li2024prlhf}. It does not study external memory or task
outcomes from tool-using agents.

\paragraph{SPRInG.}
SPRInG is the closest personalization method \cite{kim2026spring}. It uses a
user LoRA adapter and a retrieval buffer, then updates both over time.
Therefore, combining external memory with an adapter is not a new
contribution.

SPRInG selects training records by their change in likelihood. Records that
remain hard after training enter its buffer. It does not use the same evidence
to build matched context and parameter versions, then select one on later
tasks.

\paragraph{EvolveR.}
EvolveR summarizes lessons from agent trajectories and stores them in an
external Experience Base \cite{wu2025evolver}. It also tests learning these
lessons in model parameters. The reported average score falls from \(0.382\)
to \(0.371\). This result suggests that writing unfiltered experience into
parameters can add noise.

\paragraph{CoSteer.}
CoSteer does not train user parameters \cite{lv2025costeer}. A local model
runs with and without private user context. The difference between those
outputs steers a cloud model. CoSteer shows why a runtime method should remain
a baseline.

\section{Proposed Test}

At time \(t\), user \(u\) has adapter \(\adapter^{(t)}\) and external memory
\(\memory^{(t)}\). Let \(E_t\) be new evidence from later interactions.

\paragraph{Context version.}
\begin{equation}
  M_{u,\mathrm{ctx}}
  =\operatorname{MemoryUpdate}\!\left(\memory^{(t)},E_t\right),
  \qquad
  \Delta\theta_{u,\mathrm{ctx}}=\adapter^{(t)}.
\end{equation}

\paragraph{Parameter version.}
\begin{equation}
  \Delta\theta_{u,\mathrm{par}}
  =\operatorname{TrainAdapter}\!\left(\adapter^{(t)},E_t\right),
  \qquad
  M_{u,\mathrm{par}}=\memory^{(t)}.
\end{equation}

The two versions must use the same evidence, starting model, and later tasks
\(V_t\). The parameter version cannot receive \(E_t\) in its test prompt.
Otherwise, the test cannot show what the adapter learned.

Use two selection conditions:
\begin{equation}
  \begin{aligned}
  \prefscore(m_{\mathrm{par}};V_t)
    &> \prefscore(m_{\mathrm{ctx}};V_t),\\
  \taskscore(m_{\mathrm{par}};V_t)
    &\ge \taskscore(m_{\mathrm{ctx}};V_t).
  \end{aligned}
\end{equation}

Choose the parameter version only when both conditions hold. Otherwise, choose
the context version. Do not update when the evidence is too limited or
contradictory.

This rule belongs to the proposed experiment. It is not a finding from the
papers above.

\section{Experiment}

\subsection{Split the data by time}

Order complete sessions before extracting profiles or creating training data:
\begin{equation}
  H_u^{\mathrm{past}}
  \prec E_t
  \prec V_t
  \prec H_u^{\mathrm{test}}.
\end{equation}
Use past records for initialization. Use \(E_t\) to build the two versions.
Use \(V_t\) to select one. Keep the final period untouched for testing.

\subsection{Minimum baselines}

  \centering
  \caption{Baselines needed for the first experiment.}
  \begin{tabularx}{0.94\textwidth}{@{}L{0.32\textwidth}Y@{}}
    \toprule
    Version & Question \\
    \midrule
    Base model & What happens without personalization? \\
    Base model with prompt or memory & What can context do without training? \\

    Adapter with prompt or memory & Do the two forms help each other? \\
    OPPU & Is standard per-user PEFT enough? \\

    CoSteer, when practical & Can runtime steering avoid training? \\
    Proposed test & Does choosing where to store evidence improve results? \\
    \bottomrule
  \end{tabularx}

Report three outcomes separately:
\begin{itemize}
  \item personalization on later tasks;
  \item task success verified by the environment; and
  \item prompt, training, and inference cost.
\end{itemize}
Do not combine them into one score. Use confidence intervals only to show how
stable the results are.

\section{Novelty Boundary}

The following ideas already exist:
\begin{itemize}
  \item one adapter for each user;
  \item continued updates to a user adapter;
  \item external memory used with an adapter; and
  \item comparisons between context and parameter learning.
\end{itemize}

The possible new point is narrower. Use the same evidence to build a context
version and a parameter version. Then use the same user's later tasks to
decide where that evidence should stay.

This difference still needs a broader literature review and an experiment.
For now, it is a research hypothesis.

\section{Next Steps}

\begin{enumerate}
  \item Select same-user data with reliable timestamps.
  \item Implement OPPU, SPRInG, and prompt or memory baselines from their
  papers or official code.
  \item Fix one adapter training method and one memory update method.
  \item Run the base, context-only, adapter-only, and combined versions.
  \item Run the matched comparison proposed in this note.
  \item Extend to tool-using agent tasks only after personalization and task
  success both hold.
\end{enumerate}

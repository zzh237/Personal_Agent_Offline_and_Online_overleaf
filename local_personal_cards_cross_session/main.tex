\title{\method: Local Preference Learning and Cross-Session Transfer for Frozen Language Models}
\author{Anonymous Authors}

\begin{document}
\maketitle

\begin{abstract}
Past corrections can guide later tasks, but replaying full chat history sends
old content to a remote model. \method{} keeps learning local. A Qwen3-0.6B
LoRA extractor turns each task, answer, and explicit correction into a
validated card. A local store transfers a rule only after two distinct sessions
support it. A fresh Claude CLI call to frozen Sonnet 4.5 then receives the
current task and compact profile, not the raw history.

We train on 914 examples from one user's archive. On 183
conversation-disjoint test examples, the extractor produces valid JSON for
every input, with 71\% task-type accuracy and 73\% feedback micro F1. The
untouched base model produces no valid card and serves only as a structural
control. A single-card diagnostic shows no gain. With repeated support, the
profile wins five of seven position-consistent comparisons across eight tasks.
Mean quality stays at 4.25, while preference fit rises from 3.4 to 4.0; both
paired intervals include zero. This establishes pipeline feasibility, not a
reliable personalization effect. The study covers one user and offers data
minimization rather than a formal privacy guarantee.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

A correction such as ``give me a table, not another long explanation'' may
matter in a later session. Retrieving the old exchange can recover that signal,
but it also sends the old task, answer, and correction to the remote model
(Figure~\ref{fig:motivation}A).

\method{} compresses this history locally. A Qwen3-0.6B extractor writes
structured cards, and a local SQLite store transfers only rules supported by
two separate sessions. Sonnet 4.5 remains frozen. Each experimental answer is
generated by a fresh Claude CLI call with no session persistence.

This design targets closed models. Personalized fine-tuning changes the model
that produces the answer \citep{li2024personalizedrlhf}. Soft-prompt and
decoding-time methods require embedding or logit access
\citep{hebert2024persoma,lv2025costeer}. Our executor exposes neither. A
readable profile remains inspectable and works through an ordinary prompt.

The present study is a one-user, eight-task pilot. We report the failed
single-card transfer, the repeated-support result, its uncertainty, and concrete
failure cases. The paper contributes:

    \item a distinct-source gate that blocks one-off rules before they reach
    Claude CLI; and
    \item an order-swapped cross-session pilot reporting quality, preference
    fit, uncertainty, latency, cost, and failures.
\end{itemize}

\section{Related Work}
\label{sec:related}

\paragraph{Learning preferences from feedback.}
P-RLHF learns personalized language or reward models from user-specific
feedback \citep{li2024personalizedrlhf}. CIPHER infers preferences from user
edits \citep{gao2024cipher}. We instead freeze the remote executor and train a
small local model to produce an inspectable record. Repeated support prevents
one correction from becoming a durable rule.

\paragraph{Personalization at the model interface.}
PERSOMA compresses history into learned soft prompts
\citep{hebert2024persoma}. CoSteer changes a cloud model's token distribution
with a local delta model \citep{lv2025costeer}. These methods need access that a
prompt-only API does not expose. LaMP studies retrieval-based personalization
across users and tasks \citep{salemi2023lampwl}. Memory systems such as MemGPT
and Mem0 also carry information across sessions
\citep{packer2023memgpttl,chhikara2025mem0bp}. We send a short supported
profile instead of the old conversation.

\paragraph{Evaluation.}
LLM judges show position bias, so we judge each pair in both orders
\citep{zheng2023judginglw}. Judges can also favor generations from their own
model family \citep{panickssery2024llmer}. Sonnet 4.5 is both executor and
judge in our study, so we report that risk and retain every inconsistent pair.
Paired bootstrap intervals make the uncertainty from eight tasks explicit
\citep{efron1979bootstrapma}.

\label{sec:method}

\subsection{Local and Remote Contract}

Let a historical observation be
\[
o=(x,a,f,r),
\]
where $x$ is the earlier task, $a$ is the assistant answer, $f$ is the user's
feedback, and $r$ records whether a revised answer passed a deterministic
check. The local extractor $E_\theta$ returns a card $c=E_\theta(o)$. For a new
task $x'$ of type $\tau$, the frozen executor $R$ produces
\[
y_{\mathrm{base}}=R(x'), \qquad
y_{\mathrm{profile}}=R(P_\tau,x'),
\]
where $P_\tau$ is the locally rendered profile. The executor never receives
$o$, the card evidence sentence, source hashes, or conversation IDs.

\subsection{Claude CLI Executor}

The remote endpoint is a Claude CLI process running Sonnet 4.5 through Amazon
Bedrock. Each baseline, profile, and judge call starts separately with
\texttt{--safe-mode} and \texttt{--no-session-persistence}. Baseline and profile
calls receive the same task; only the profile system prompt differs. The adapter
records the model, cost, duration, and full JSON envelope. The exact command and
prompts appear in Appendix~\ref{app:prompts-data}.

\subsection{Personal Card and Evidence Types}

Each card is a JSON object with ten required fields. Table~\ref{tab:schema}
groups them by purpose. The extractor emits the card only; it never answers the
task.

\toprule

Purpose & Fields \\
\midrule

\texttt{likert}, \texttt{confidence}, \texttt{scope} \\
Transfer & \texttt{instruction} \\

\bottomrule

The evidence contract has three classes:
\begin{itemize}[leftmargin=1.4em,itemsep=2pt,topsep=3pt]
    \item \texttt{explicit\_correction}: a real corrective user message;
    \item \texttt{verified\_revision}: an assistant revision that passes a
    deterministic requested-change check; and
    \item \texttt{category\_label}: a task label with no preference evidence.
\end{itemize}
The last class trains abstention. It uses direction \texttt{uncertain},
Likert~3, confidence~0.4, task-instance scope, and an instruction not to infer
a lasting preference. These cards are never eligible for transfer. A verified
revision is weaker than direct user approval.

\subsection{Local Training}

The archive builder creates targets with deterministic local rules. Explicit
corrections produce negative examples. A revision is added as a weak positive
only when it passes the requested-change check. Category-only rows teach task
classification without a preference claim. Conversation IDs, not individual
rows, define the train, validation, and test splits.

We freeze Qwen3-0.6B \citep{yang2025qwen3tr} and train LoRA modules
\citep{hu2022lora} on \texttt{q\_proj}, \texttt{k\_proj},
\texttt{v\_proj}, and \texttt{o\_proj}. Only target JSON tokens enter the
loss:
\begin{equation}
\mathcal{L}(\theta)
=-\frac{1}{|T_c|}\sum_{t\in T_c}
\log p_\theta(y_t\mid y_{<t},o),
\label{eq:sft}
\end{equation}
where $T_c$ indexes the card completion. Prompt and observation tokens remain
visible through attention but receive label $-100$.

\subsection{Repeated-Support Profile}

The local store rejects category-only cards, uncertain directions, confidence
below 0.65, and task-instance scope. For an exact instruction $u$, let $H(u)$
be its distinct evidence hashes. Its support is
\[
\operatorname{supp}(u)=|H(u)|.
\]
An instruction can leave the device only when
\begin{equation}
\operatorname{supp}(u)\geq 2.
\label{eq:support}
\end{equation}
Candidates are ranked by
\begin{equation}
s(u)=\sum_{i:u_i=u}\gamma_i w(e_i), \qquad
w(e_i)=
\begin{cases}
1,&e_i=\texttt{explicit\_correction},\\
0.5,&e_i=\texttt{verified\_revision},
\end{cases}
\label{eq:rank}
\end{equation}
with duplicate hashes counted once. The store keeps at most three rules and
skips a lower-ranked rule if it adds no feedback facet.

The rendered profile contains the task type, each selected instruction, its
facets, support count, mean confidence, mean Likert value, scope, and a policy
that the current request overrides the profile. It contains no raw
conversation or evidence text. The method reduces what is sent, but the profile
is still personal information.

\subsection{Card Extraction}

The LoRA adapter and untouched base model receive the same extraction prompt,
183 test examples, greedy decoding settings, and validator. We report
valid-card rate, task-type accuracy, direction accuracy, exact Likert accuracy,
scope accuracy, exact feedback-set accuracy, and feedback micro F1. Invalid
outputs score zero on field metrics. The untouched model is a format-and-task
control, not a competitive instruction-tuned baseline.

\subsection{Cross-Session Transfer Pilot}

The first diagnostic applies one eligible card to one new task of the same
type. Its eight task IDs are then excluded from the main run.

After filtering, 74 cards populate the store. The selector freezes eight new
tasks from a separate holdout file and rejects tasks that need missing files or
context. For each task, two fresh Claude CLI calls produce the baseline and
profile answers. Two more calls judge the pair with answer order reversed. A
verdict counts only when both orders select the same answer.

We average the two judge orders for each condition and compute paired deltas.
We then bootstrap the eight paired tasks 20,000 times and report 95\%
intervals.

\subsection{Scale of the Next Study}
\label{sec:confirmatory-design}

The current run tests feasibility, not effect size. The confirmatory study will
use at least 20 users and 50 new tasks per user. Five conditions, three samples,
and three executor families yield at least 45,000 answers before judging.
Blinded humans and a separate model family will judge the outputs. Appendix
\ref{app:confirmatory} gives the full design.

\subsection{Single Cards Do Not Transfer Reliably}

The single-card diagnostic yields three profile wins, three baseline wins, one
tie, and one position-inconsistent pair. Manual inspection shows a recurring
problem: a single correction can preserve a file name, number, or detail that
should not move to another task. This result motivated the support gate in
Eq.~\eqref{eq:support}.

\subsection{Repeated Support Gives a Positive but Uncertain Signal}

The repeated-support profile wins five of seven position-consistent
comparisons. Mean task quality is unchanged. Mean preference fit is 0.63 points
higher with the profile.

\subsection{Cost and Failure Analysis}

The profile adds 4.9 seconds of mean executor latency. The full experiment
uses 16 executor calls and 16 judge calls and costs \$1.92. These values
describe this task set and profile length; they do not isolate the cause of the
latency difference.

The manual audit finds clear profile wins on repository-upload instructions, a
short translation, campaign questions, and a Newton-convergence explanation.
It also identifies three distinct failures. The guided least-squares answer
contains an arithmetic error. Both answers to the degrees-of-freedom question
are too broad. The foreign-key pair changes winner when answer order is
reversed and is therefore reported as inconsistent.

An attempted Qwen2.5-7B rewriting teacher mostly produced task-instance rules
and was cancelled before student training. We do not count it as an ablation.

\section{Discussion and Limitations}
\label{sec:discussion}

The strongest result is local extraction. A 0.6B model learns the card schema
and abstention behavior in a few GPU minutes. Its 71\% task-type accuracy can
route cards to the wrong profile bucket. Its 64\% exact feedback-set accuracy
can also change which rules survive facet deduplication.

Repeated support is a useful transfer gate because it is simple and auditable.
It does not recognize paraphrases: two semantically identical instructions
count as different strings. The failed 7B branch shows the opposite risk:
learned rewriting may over-generalize or copy one-off details. A better method
should group paraphrases while preserving source-level support.

The online stage changes local memory, not model weights. The pilot covers one
user and eight tasks. Sonnet 4.5 serves as executor and judge, and the judge
sees the profile used to guide one answer. Preference fit therefore measures
compliance with the displayed profile, not independent user satisfaction.
Human judgments and a cross-family judge are needed for stronger claims.

Finally, local storage is not a formal privacy guarantee. Raw history and
evidence text stay on the device, but instructions, support counts, confidence,
Likert summaries, facets, and scope are sent to the remote model. We provide no
differential-privacy or cryptographic guarantee
\citep{dwork2006calibratingnt}. The source archive is private and cannot be
released without review and consent.

\section{Conclusion}

We built a complete path from historical corrections to a local card store and
fresh Claude CLI calls to a frozen model. The extractor reliably produces valid
cards. Single-card transfer fails; repeated support gives a positive but
uncertain signal on eight tasks. This is a feasibility prototype. Stronger
claims require the larger multi-user study described above.
